## 1. Протокол Agentic TDD (`Red → Green → Refactor`)

Ніколи не просіть агента писати робочий код і тести в одному повідомленні — це породжує спільну сліпу пляму або «підгонку тестів під відповідь».

| Фаза | Дозволено агенту | Суворо заборонено | Контрольна дія Архітектора |
|---|---|---|---|
| **1. Red (Червона)** | Читати ТЗ, писати тести у `tests/` на основні й крайові сценарії | Змінювати будь-які файли у `src/` | Запустити `!pytest` / `!npx vitest run` і **очима перевірити**, що тести впали через відсутність фічі (а не синтаксис імпорту) |
| **2. Green (Зелена)** | Писати й правити реалізацію у `src/`, проганяти тести у циклі | Торкатися будь-яких файлів у `tests/` | Переконатися у зеленому прогоні + виконати **`!git diff tests/`** (має бути порожньо!) |
| **3. Refactor (Чистова)** | Прибирати дублювання, виносити константи, викликати `/simplify` | Ламати бізнес-контракти та тести | Прогнати повну команду верифікації проєкту (`make check` / `npm run verify`) |

## 2. Чотиришарова піраміда верифікації проєкту

Замкніть усі шари в одну атомарну команду з коротким виводом помилок (`pytest -q --tb=short`), щоб агент сам виправляв більшість похибок без спалювання контексту:

1. **Статична типізація (~0.3–0.5с):** `pyright` / `mypy --strict` (Python) або `tsc --noEmit` (TypeScript) — миттєво ловить вигадані методи та необроблені `None` / `undefined`.
2. **Швидкі Rust-лінтери (~0.1с):** `ruff check .` (Python) або `biome check .` (TS/JS) — вичищає мертві імпорти, забуті змінні та антипатерни.
3. **Юніт та інтеграційні тести (~3–10с):** `pytest` / `vitest` (для критичної логіки — на реальній тестовій БД у контейнері, а не поверх паперових моків).
4. **Живий Smoke Test (~5–15с):** фоновий старт сервісу + `curl -fsS http://localhost:8001/health` та перевірка JSON-відповіді (або візуальна перевірка UI й консолі браузера через **`claude --chrome`**).

## 3. Паралельна інженерія з `Git Worktrees`

Один спільний каталог історії `.git`, але кілька повністю ізольованих робочих папок для різних гілок — жодного `git stash` і конфліктів під час роботи кількох агентів!

- **Швидкий запуск ізольованої сесії:** `claude --worktree <task-name>` або коротко **`claude -w <task-name>`** (створює дерево у `.claude/worktrees/<task-name>`).
- **Ізоляція декларативних субагентів:** додайте `isolation: "worktree"` у frontmatter файлу `.claude/agents/<name>.md`.
- **Ручне керування Git:**
  - Список активних дерев: `git worktree list`
  - Видалення після злиття гілки: `git worktree remove <шлях>` та очищення метаданих `git worktree prune`
  - У панелі `claude agents`: клавіші **`Ctrl + X`** безпечно видаляють відпрацьований worktree (із захистом від втрати незапушених комітів).
- **Чотири інженерні застереження:**
  1. **1 гілка = 1 worktree** (не можна відкрити ту саму гілку у двох деревах одночасно).
  2. Файли з `.gitignore` (`.env`) не копіюються самі — підключайте тестовий шаблон або хук `WorktreeCreate`.
  3. Розводьте мережеві порти паралельних стендів (`8001`, `8002` замість спільного `8000`).
  4. Ніколи не тримайте репозиторій у Google Drive / Dropbox / iCloud — хмарна синхронізація ламає посилання `worktree`.

## 4. Команди код-рев'ю у Claude Code (`v2.1.316+`, осінь 2026)

| Команда | Призначення | Коли використовувати |
|---|---|---|
| **`/simplify`** | Вбудована навичка чистоти: прибирає дублювання, зайву вкладеність і покращує читабельність (**не шукає баги!**) | Одразу після зеленої фази TDD перед фінальним рев'ю |
| **`/code-review <level>`** *(синонім `/review`)* | Локальний прицільний пошук багів коректності на рівні зусиль `low`, `medium`, `high`, `xhigh`, `max` (опції `--fix`, `--comment`) | Щоденна перевірка модулів перед комітом (`medium` для дрібних правок, `high`/`max` для складної логіки) |
| **`/code-review ultra`** *(синонім `/ultrareview`)* | **Глибоке хмарне мультиагентне рев'ю:** кілька агентів у хмарі шукають стани гонитви, дірки безпеки, витоки ресурсів і зламані контракти + фінальний агент-верифікатор відсіває хибні тривоги | Перед створенням відповідального Pull Request (платежі, авторизація, міграції БД, конкурентний код) |

## 5. Матриця аварійного порятунку та діагностики

- **Три хірургічні режими `Esc + Esc` (`/rewind`):**
  1. **Відкотити ТІЛЬКИ код** — діагностика у чаті правильна й цінна, але спроба правки коду невдала.
  2. **Відкотити ТІЛЬКИ діалог** — файли вже написані ідеально, треба лише відрізати зайве обговорення з контексту.
  3. **Відкотити І код, І діалог** — нечітке ТЗ, агент із першої хвилини пішов не туди (чистий старт без сміття в пам'яті).
- **Правило 3 спроб проти «петлі смерті»:** якщо 3 правки поспіль не зрушили ту саму помилку — **СТОП**! Відкат `/rewind` → `Shift+Tab` (`Plan Mode`) → `/model opus` → запит: *«Код не пиши, поясни першопричину падіння»*.
- **Зупинка завислих фонових агентів:** `claude agents` → знайти сесію (`Ctrl + F` — пошук за назвою) → `claude stop <id>` (або `claude kill <id>`); усі фонові агенти одразу — `Ctrl+X Ctrl+K`.
- **Карантин для незавершеної роботи:** ніколи не комітьте зламаний код у `main`! Евакуюйте у гілку `wip/<task>` та збережіть на сервері: `git checkout -b wip/<task> && git push -u origin wip/<task>`.
- **Бортова діагностика:** `/doctor` (`/checkup`), `/doctor prompt-audit`, `/debug`, `/cost`, `/usage`, `/memory`.

## 6. Командний стандарт Git Архітектора

1. **Conventional Commits («чому», а не «що»):** `feat(scope): ...`, `fix(scope): ...`, `refactor(scope): ...` із поясненням причини архітектурного вибору у тілі коміту.
2. **Стерильний індекс (ТАБУ на сліпий `git add .`):** спершу `git status`, поіменний `git add <свої-файли>`, перевірка `git diff --staged`, питання користувачу щодо сторонніх незакомічених файлів + обов'язковий скан на секрети (`.env`, `*.pem`, `*.key`, `credentials*`, `client_secret*`).
3. **Чиста історія та контури пушу:** `rebase` + `squash` чорнових `wip/`-гілок перед влиттям у `main`. У власних репо (`~/Projects`) — автопуш для синхронізації машин; у корпоративних (`~/Work`) — **завжди питати підтвердження перед `git push`** (запускає CI/CD).
4. **Фінальна крапка задачі:** структурований PR через `gh pr create` та ідеально чистий `git status`.

## 7. Підсумковий практикум Фіналу Сезону 1

- 🟢 **Базовий рівень:** Візьміть невелику задачу у своєму проєкті й проведіть її за 3 кроками TDD (`Red` у `tests/` без зміни `src/` → `Green` із забороною чіпати `tests/` та перевіркою `!git diff tests/` → `Refactor`). Спеціально протестуйте на навчальній правці всі 3 режими `Esc + Esc` (`/rewind`).
- 🟡 **Поглиблений рівень:** Об'єднайте 4 шари верифікації свого проєкту в єдину команду (`make check` або `npm run verify`). Запустіть паралельно 2 ізольовані задачі через `claude -w`, доведіть одну до злиття з точковим Conventional Commit (без `git add .`) і штатно приберіть відпрацьоване дерево через `git worktree remove`.
- 🔴 **Архітектурний екзамен Сезону 1:** Проведіть повноцінну продакшн-фічу за наскрізним конвеєром усіх 5 серій: чистий старт у `Auto Mode` з лаконічним `CLAUDE.md` → ізольований `claude -w` → декомпозиція через `opusplan` у `Plan Mode` із точковим `/subtask` → реалізація за TDD та 4 шарами перевірки → фокусний `/compact` → шліфовка `/simplify` та аудит через `/code-review high` або `/code-review ultra` → оформлення еталонного PR за чеклістом `PR-VERIFICATION-CHECKLIST.md` та чистий `git status`!

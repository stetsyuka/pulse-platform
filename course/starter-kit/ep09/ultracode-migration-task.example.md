# Шаблон задачі для масового воркфлоу `/effort ultracode` (Dynamic Workflows)

> **Коли використовувати:** Однотипні інженерні операції на масштабі **15–200+ модулів/файлів** (міграція мажорної версії SDK, уніфікація обробки помилок, аудит API-ендпоінтів, додавання контракту телеметрії).
>
> **Перед запуском у терміналі:**
> ```bash
> export CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL=sonnet
> export CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=15
> ```
> Усередині сесії Claude Code увімкніть режим оркестрації:
> ```text
> /effort ultracode
> ```

---

## Промпт-контракт для запуску `ultracode`

Скопіюйте або передайте через `@ultracode-migration-task.example.md` наступне завдання:

```markdown
### Задача: Пакетна міграція HTTP-клієнта у мікросервісах та обробниках (`v1 Legacy` → `v2 Typed Client`)

Виконай масову контрольовану міграцію всіх модулів у `src/services/**/*.ts` та `src/handlers/**/*.ts` за допомогою динамічного воркфлоу (`ultracode`):

#### Крок 1. Інвентаризація (Map Phase Discovery)
1. Знайди всі файли у `src/services/` та `src/handlers/`, які імпортують застарілий клієнт `@internal/http-legacy` або використовують нетипізований `legacyFetch(...)`.
2. Згрупуй знайдені файли у незалежні пакети (batches) по 5 файлів на одного воркера. Не перетинай межі одного доменного модуля між різними воркерами.

#### Крок 2. Контракт трансформації для кожного воркера (Worker Execution)
Для кожного пакета файлів запусти ізольованого субагента-воркера з чітким алгоритмом:
1. Замінити імпорт `@internal/http-legacy` на `@internal/http-v2` (`createTypedClient`).
2. Перевести виклики `legacyFetch(url, { timeout, headers })` на новий контракт `apiClient.request<ResponseSchema>({ path, timeoutMs, headers })` зі збереженням існуючих таймаутів.
3. Замінити перехоплення `LegacyHttpError` на `HttpClientError` з перевіркою `err.statusCode` та збереженням `correlationId` у логах.
4. Запустити таргетовану перевірку типів і юніт-тестів виключно для зміненого пакета:
   - `pnpm tsc --noEmit`
   - `pnpm vitest run <відповідні_тести_модуля>`
5. Якщо тест або типізація падає — воркер має максимум 2 спроби самовиправлення. Якщо після 2 спроб помилка залишається — відкотити зміни у проблемному файлі (`git checkout -- <file>`) і зафіксувати причину у звіті воркера.

#### Крок 3. Зведена верифікація та звіт (Reduce Phase)
Після завершення всіх паралельних воркерів:
1. Запусти загальний `pnpm typecheck && pnpm test:ci`.
2. Згенеруй підсумковий звіт у `docs/migrations/http-v2-report.md`:
   - Загальна кількість знайдених / успішно змігрованих / пропущених файлів.
   - Таблиця всіх змінених модулів зі статусом тестів (`PASS` / `NEEDS_MANUAL_REVIEW`).
   - Детальний опис крайніх випадків (edge cases), які потребують ручного рішення архітектора.
```

## Моніторинг під час виконання

- Перевірити статус виконання згенерованого JS-оркестратора та активних пакетів:
  ```text
  /workflows
  ```
- Повернутися у стандартний режим після завершення масової операції:
  ```text
  /effort high
  ```
